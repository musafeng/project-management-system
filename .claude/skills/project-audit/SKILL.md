# 项目审计 Skill

## 何时调用

- 接手一块陌生模块前
- 计划做较大改动前（哪怕只是 UI 改造）
- 用户问"这块代码现在状态如何"
- 怀疑某个能力有隐性 bug 或回归风险
- 评估"能不能改 / 该不该改"

## 审计流程

按以下顺序执行，**不要跳步**：

### 1. 确定审计范围

先和用户对齐范围：是单个文件、单个业务表、单个 API、还是整条链路（如"附件上传链路"）。范围越窄，结论越可用。

### 2. 收集事实

只读，不改。需要收集：

- **入口文件清单**：相关 page、route、component
- **数据流图**：从用户操作 → 前端组件 → API → DB → 回写到 UI 的完整路径
- **依赖关系**：被谁调用、调用了谁
- **历史变更**：`git log --oneline -- <path>` 看最近 20 条
- **注释中的告警**：搜索 `TODO`、`FIXME`、`HACK`、`XXX`、`临时`、`待修`
- **类型边界**：Prisma model、Zod schema、TS interface 是否一致
- **异常处理**：try/catch 覆盖度、是否吞错

### 3. 识别风险

按以下维度逐项过：

| 维度 | 问的问题 |
|------|----------|
| 数据正确性 | 金额、数量、时间是否可能算错？精度处理是否一致？ |
| 区域/权限 | 跨区域查询是否正确隔离？admin/普通用户是否分离？ |
| 并发 | 是否存在 race condition？审批/支付能否双击触发两次？ |
| 安全 | 是否有 SQL 注入风险？文件上传是否限制类型/大小？签名链接是否过期？ |
| 移动端 | 在 375px 窗口下是否可用？ |
| 钉钉 | access_token 缓存是否一致？工作通知是否会重复发？ |
| 一致性 | 同类业务（如 6 类付款）实现是否对齐？ |
| 可观测性 | 出错时能不能在日志/动作记录里查到原因？ |

### 4. 输出审计结论

回复用户时按这个结构：

```
【审计范围】
【现状】（事实，不带主观）
【风险点】（按严重度排）
【改 vs 不改的建议】
【若改，建议的最小改动方案】
【若改，必须避开的坑】
```

## 必须遵守

- **只读不写**。审计阶段禁止改任何文件，除非用户明确点头。
- **不输出 Markdown 文档文件**。结论直接放在对话里，除非用户要求 `*.md` 留档。
- **不臆造**。看不到的代码不要猜，不确定的部分明确写"未确认"。
- **结合 CLAUDE.md 第四节"严禁破坏的核心能力"**。如果审计目标涉及审批、收付款、附件、登录、权限，风险等级直接拉高一档。

## 输出节制

- 单次审计回复控制在 60 行内
- 不要复述用户的话
- 不要写"这是一份完整的审计"之类的元描述
